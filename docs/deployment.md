# Deploying AutoX as a public demo

The plan, before any host is chosen. AutoX is going up as a **portfolio demonstration**:
invented listings, no real users, accounts not for real use. That settles several questions
the general case would leave open, and the plan below is written for it — where a choice
would be different for a real marketplace, it says so.

Nothing here has been deployed. Section 5 lists what has to change in the repository first;
none of it is large.

---

## 1. What runs where

Four pieces. Each can be swapped without touching the others.

```
 browser ──► static site  (Angular build: files + _headers + _redirects)
    │
    ├──────► API          (Spring Boot jar, Java 21, one container)  ──► PostgreSQL 16
    │                                                                 └─► object storage
    └──────► object storage (photos: read by signed or public URL, uploaded by pre-signed PUT)
```

### The API — a container host

| Need | Why |
|---|---|
| **Java 21**, run as `java -jar` from a container image | There is no Dockerfile yet (§5.1). |
| **1 GB of memory**, 512 MB as a floor | Photos are decoded and resized in the JVM: a 10 MB JPEG becomes a ~50 MB bitmap while its three sizes are made. |
| **Always on**, not scale-to-zero | Start-up is 10–20 s (JVM, Flyway, Hibernate validation), which a visitor sees as a dead site; and the expiry and clean-up sweepers only run while the process does. A free tier that sleeps is workable for a demo if the first-visit delay is acceptable. |
| **One instance** | Enough by a wide margin. More would also work — the sweepers take a database lock — but buys nothing here. |
| **HTTPS terminated in front**, with a proxy you can trust to set `X-Forwarded-For` | See §5.2: this is the one configuration change that is not optional. |
| A health check on `/actuator/health/readiness` | Public, status only. |

Typical fits: any PaaS that runs a container image (Fly.io, Render, Railway, Koyeb, Scaleway
Serverless Containers, Google Cloud Run with min-instances 1), or a small VM with Docker.

### The database — managed PostgreSQL 16

- **Any managed PostgreSQL 16.** The schema needs nothing beyond core PostgreSQL. Flyway creates
  it on first start; the user needs ordinary DDL rights on its own database, not superuser.
- **Size is trivial**: sixty demo listings and their history fit in a few megabytes. The
  smallest tier of any provider is enough.
- **Connections:** the pool opens up to 10 (`AUTOX_DB_POOL_SIZE`). Some free tiers cap
  connections near that; set the pool to 5 there.
- **TLS:** add `?sslmode=require` to the JDBC URL. Providers that give a `postgres://` URL
  need it rewritten as `jdbc:postgresql://host:port/db?sslmode=require`, with the user and
  password in their own variables.
- **Backups:** for a demo, the provider's default is enough — the content is regenerated by
  the seed (§4).

Typical fits: Neon, Supabase, the database offering of whichever host runs the API.

### Object storage — any S3-compatible bucket

The application speaks the S3 API and nothing vendor-specific: MinIO locally, and in
production Cloudflare R2, Backblaze B2, Scaleway Object Storage or AWS S3 are all
configuration. What it needs from the provider:

- **Pre-signed PUT and GET.** Every provider above supports both.
- **A CORS rule on the bucket** allowing `PUT` and `GET` from the site's origin (§5.4). Without
  it every photo upload fails in the browser, and nothing on the server notices.
- **Private by default.** Photos are served through URLs the API signs, valid six hours. A
  public bucket or CDN in front (`AUTOX_S3_PUBLIC_BASE_URL`) makes them cacheable — worth it
  for performance, not needed for a demo.

**For this demo, R2 is the natural fit**: no egress charges (a gallery is mostly egress), a
free allowance far above sixty listings' worth of photos, and path-style access on one host,
which keeps the security policy to a single storage origin.

### The site — a static host that honours `_headers`

`npm run build` produces a folder of files. It writes the security headers into `_headers`
(the format **Cloudflare Pages** and **Netlify** read) and an SPA fallback into `_redirects`
and `404.html`. On those two, the headers apply with no further work.

On any other host — Vercel, an S3 website, nginx, Caddy — the same headers must be configured
by hand: `scripts/security-headers.mjs` is the source, and `npm run build` prints the policy.
The policy is also written into the page as a `<meta>`, so even a host that sets no headers at
all gets the part of it that matters most; it loses `frame-ancestors` and HSTS.

### One origin or two

- **Two origins** (site on a static host, API on its own domain) is the simple path and the
  one this plan assumes. It needs CORS on the API (`AUTOX_CORS_ALLOWED_ORIGINS`) and the
  API's address at build time (`AUTOX_API_BASE_URL`).
- **One origin** (a proxy routing `/api/*` to the API and everything else to the files) needs
  neither, and makes the policy one origin shorter. Worth it if the chosen host makes it easy;
  not worth building a proxy for.

## 2. Environment variables

### The API

Required — the application refuses to start without them, naming the one missing:

| Variable | Production value |
|---|---|
| `AUTOX_DB_URL` | `jdbc:postgresql://<host>:<port>/<db>?sslmode=require` |
| `AUTOX_DB_USERNAME`, `AUTOX_DB_PASSWORD` | From the provider. |
| `AUTOX_JWT_SECRET` | New, random, ≥ 32 bytes: `openssl rand -base64 48`. Never the local one. |
| `AUTOX_S3_ACCESS_KEY`, `AUTOX_S3_SECRET_KEY` | A key scoped to **this bucket only**, read and write. |

Set explicitly, because the default is wrong for production:

| Variable | Value | Default, and why it is wrong here |
|---|---|---|
| `AUTOX_S3_ENDPOINT` | The provider's S3 endpoint, e.g. `https://<account>.r2.cloudflarestorage.com` | empty |
| `AUTOX_S3_REGION` | `auto` for R2; the bucket's region elsewhere | `us-east-1` |
| `AUTOX_S3_BUCKET` | The bucket's name | `autox-images` |
| `AUTOX_S3_PATH_STYLE` | `true` for R2 and MinIO; `false` for AWS | `false` |
| `AUTOX_S3_CREATE_BUCKET` | `false` — create it in the provider's console, with its CORS rule | `false` |
| `AUTOX_CORS_ALLOWED_ORIGINS` | The site's origin, e.g. `https://autox.example.com` | `http://localhost:4200` |
| `AUTOX_PASSWORD_RESET_URL` | `https://<site>/reinitialiser-mot-de-passe` | localhost |
| `AUTOX_JWT_ISSUER` | The API's URL | `https://api.autox.local` |
| `AUTOX_LOG_LEVEL` | `INFO` | `INFO` — but `.env.example` says `DEBUG`; do not copy it |
| `AUTOX_PORT` | Whatever the host expects, often `8080` or `$PORT` | `8080` |

For the demo specifically — Spring's relaxed binding maps these onto properties that have no
`${…}` placeholder of their own:

| Variable | Suggested | Why |
|---|---|---|
| `AUTOX_LISTING_EXPIRYDAYS` | `3650` | Listings expire after 60 days, and the seed does not renew them: without this the demo empties itself two months after it is seeded. |
| `AUTOX_LISTING_PROFESSIONNELACTIVELIMIT` | `3` | Dealers are uncapped (`0`), and anyone can register as one. On a public demo that is a way to flood it. |
| `AUTOX_LISTING_PARTICULIERACTIVELIMIT` | `3` | Five is the product's number; three is plenty for someone trying the flow. |
| `AUTOX_REGISTRATION_MAX_ATTEMPTS` | `5` (the default) | Per address per hour. |

Left at their defaults: `AUTOX_MAIL_PROVIDER=log` (see §6), the throttles (`…_ENABLED=true`),
`AUTOX_DB_POOL_SIZE` unless the provider caps connections.

### The site — at build time, not at run time

A static site has no server to read configuration from, so these are compiled in by
`npm run build`:

| Variable | Value |
|---|---|
| `AUTOX_API_BASE_URL` | The API's origin, e.g. `https://api.autox.example.com`. Empty for one-origin. |
| `AUTOX_STORAGE_ORIGINS` | Every origin photos are read from or uploaded to, separated by spaces: the S3 endpoint, plus the public base URL if one is set. For R2 with path-style: `https://<account>.r2.cloudflarestorage.com`. |
| `AUTOX_SITE_URL` | The site's own origin. Makes the link-preview image absolute and turns HSTS on. |

Get `AUTOX_STORAGE_ORIGINS` wrong and photos do not load and uploads fail — with a clear
message in the browser console, and nothing on the server. It is the first thing to check if
images are missing after a deploy.

## 3. Order of operations

1. **Storage.** Create the bucket, private. Add the CORS rule (§5.4). Create a key scoped to it.
2. **Database.** Create it. Note the JDBC URL with `sslmode=require`.
3. **API.** Build the image (§5.1), set every variable in §2, deploy, and wait for
   `/actuator/health/readiness` to answer `UP`. Flyway creates the schema on this first start.
4. **Seed** (§4).
5. **Site.** Build with the three variables, deploy the folder, open it, sign in.
6. **Promote an administrator** (README, "An administrator account"), against the production
   database.
7. **Check from outside:** a scanner such as securityheaders.com on the site; a link pasted
   into a messaging app, to see the preview; the browser console on the home page, a listing
   page and the photo step of the seller flow, which between them touch every origin.

## 4. The demo data

Run the API **once** with `SPRING_PROFILES_ACTIVE=demo` and `AUTOX_DEMO_ACTION=seed`, wait for
"Seeded" in the log (about ninety seconds: 180 real uploads and resizes), then **remove both
variables and restart.** The profile adds nothing to normal running, and an operator should
not leave a seeder wired to a production database.

To reset the demo — after visitors have filled it with test listings — run once with
`AUTOX_DEMO_ACTION=remove`, then once with `seed`. Removal deletes exactly what the seed
recorded; **listings visitors created are not touched by it** and need deleting through the
moderation screen or by SQL. A scheduled reset is not built (§6).

## 5. What has to change in the repository first

### 5.1 A container image for the API — needed

There is no Dockerfile. Either add one — a two-stage build: `maven:3.9-eclipse-temurin-21`
to run `mvn package -DskipTests`, then `eclipse-temurin:21-jre` running the jar as a non-root
user — or use `mvn spring-boot:build-image`, which produces an image with buildpacks and needs
no file. The first is explicit and reviewable; the second is less to maintain. Either way,
pass `-XX:MaxRAMPercentage=75` so the heap follows the container's memory limit.

### 5.2 Trusting the right `X-Forwarded-For` — needed, and the one that matters

`server.forward-headers-strategy=framework` makes Spring take the client address from
`X-Forwarded-For` — **from its first value.** Most platform proxies *append* the address they
saw to whatever the client sent, so the first value is the client's own claim. The
registration cap, the login throttle and the public rate limit all key on that address: behind
such a proxy, every one of them can be sidestepped by sending a made-up header.

The fix is configuration: `server.forward-headers-strategy=native`, which uses Tomcat's
`RemoteIpValve`, plus `server.tomcat.remoteip.internal-proxies` set to the host's proxy
addresses (or trusting exactly one hop). The valve then reads the header from the right,
skipping the proxies it knows, and stops at the first address it does not — the real client.
What to put in `internal-proxies` depends on the host, which is why it is not done yet. **Test
it after deploying**: send a request with `X-Forwarded-For: 1.2.3.4` and check, in the
`throttle_counter` table, that the key recorded is your own address and not `1.2.3.4`.

### 5.3 The image formats and sizes — nothing

Already configurable. Mentioned because it is a common surprise: JPEG and PNG only.

### 5.4 The bucket's CORS rule — in the provider, not the repository

```json
[{
  "AllowedOrigins": ["https://autox.example.com"],
  "AllowedMethods": ["GET", "PUT"],
  "AllowedHeaders": ["content-type"],
  "MaxAgeSeconds": 3600
}]
```

`content-type` because a pre-signed PUT is signed over it and the browser sends it. Local
MinIO allows every origin, which is why this never showed up in development.

### 5.5 Optional

- **The Swagger UI and `/v3/api-docs` are public.** Harmless — the endpoints are discoverable
  by using the site — and for a portfolio, arguably the point. To close them, one
  `requestMatchers(...).denyAll()` line in `SecurityConfig`.
- **A scheduled demo reset** (§4), as a job on the host running remove-then-seed weekly.

## 6. What the demo will and will not do

- **No email is sent.** "Mot de passe oublié" accepts the request and nothing arrives; the
  link is written to the API's log, which only the operator can read. Accounts are not for
  real use, and the footer says so on every page.
- **Anything a visitor publishes is public at once**, photos included, and reviewed
  afterwards. The caps in §2 bound how much; the moderation screen removes it. A visitor
  could still publish something unpleasant on your site for as long as it takes you to look.
  There is no configuration that turns publishing off (a cap of `0` means unlimited, not
  none). If that window is not acceptable, the option is review before publication —
  `PENDING_REVIEW` is reserved for it — which is new work.
- **Security headers and the policy** are in place on both the site and the API; the API
  answers every error, including the HTTP parser's own refusals, in its JSON problem format
  with no internal detail. Both are covered by tests.
- **Dependencies are scanned** on every push and weekly. Two advisories are accepted as not
  applicable and documented in `backend/.trivyignore`: they are in Spring Framework 6.2, which
  has no fixed release, and the only remedy is the move to Spring Boot 4.

See `docs/weaknesses.md` for the rest, most of which matters only with real users.
